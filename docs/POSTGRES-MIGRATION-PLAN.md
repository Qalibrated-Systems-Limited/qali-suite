# PostgreSQL Migration Plan

**Branch:** `feat/postgres-migration` (off `jeff-business-suite`)
**Status:** Design agreed, vertical slice in progress
**Date:** 2026-08-13

---

## 1. Decision summary

| Question | Answer |
|---|---|
| Target database | **PostgreSQL 16+** |
| ORM / query layer | **Drizzle ORM** |
| Scope | DB swap + fix two structural bug classes. Domain logic and module boundaries stay as-is. |
| Sequencing | One vertical slice (accounting core) end-to-end, measure, then commit to the rest |
| S/4HANA | **Rejected — category error.** See §1.1 |

### 1.1 Why S/4HANA was rejected

SAP S/4HANA is not a database. It is SAP's finished ERP *application suite*, running on
SAP HANA (a proprietary in-memory database). Neither is open source; both carry
six-figure annual licensing.

Adopting S/4HANA would not be a migration — it would mean deleting this ~251k-line
product and becoming an SAP implementation consultancy. S/4HANA is a **competitor to
this product**, not a platform for it.

PostgreSQL is the only open-source option, and the only one in the same category as
the current MongoDB.

## 2. Why migrate at all

The generic "MongoDB bad, SQL good" argument is not the reason. Two findings from the
audit of this specific codebase are.

### 2.1 Money is JavaScript floating point

Every monetary field in the ledger is `type: Number` — IEEE-754 float64. There are
**zero** uses of `Decimal128` anywhere in the codebase.

The consequence is already visible in `app/models/JournalEntry.js`:

```js
journalEntrySchema.virtual("isBalanced").get(function () {
  const debits = this.totalDebits;
  const credits = this.totalCredits;
  return Math.abs(debits - credits) < 0.01; // Allow 1 cent rounding
});
```

That tolerance is not a rounding policy — it is a workaround for float drift. In a
double-entry system it means **a journal entry can be up to one cent out of balance and
still post.** Repeated across thousands of entries, the trial balance drifts and cannot
be reconciled to source documents.

Postgres `NUMERIC(19,4)` is exact decimal arithmetic. Combined with a `CHECK` constraint
(§4.3), an unbalanced entry becomes *impossible to store*, not merely discouraged.

### 2.2 Tenant isolation is enforced by hand, 3,479 times

`companyId` appears 3,479 times across the codebase. Every query is individually
responsible for scoping itself to the right tenant. Each occurrence is an opportunity to
forget one — and forgetting one leaks one customer's financial records into another's.

This has already happened. Evidence in the current tree:

**`JournalEntry.getStatementOfAccount()`** — no tenant filter at all:

```js
const transactions = await this.find({
  status: "posted",
  "party.type": partyType,
  "party.id": partyId,
  entryDate: { $gte: startDate, $lte: endDate },
})
```

**`Account.calculateActualBalance()`** — scans every tenant's journal entries:

```js
const result = await JournalEntry.aggregate([
  { $match: { status: "posted" } },   // <- no companyId
  { $unwind: "$lines" },
  { $match: { "lines.accountId": this._id } },
```

**`getARAgingReport()` / `getAPAgingReport()`** — same pattern; the opening `$match`
is cross-tenant and only narrows to one company incidentally, via account id.

These are currently *mostly* correct by accident (account ids are company-specific), but
they are one refactor away from being wrong, and they force full-collection scans.

There is already a branch named `fix/critical-gaps-cross-tenant` in this repo. This bug
class is not hypothetical.

**Postgres Row-Level Security enforces `company_id` once, in the database.** A query that
forgets the filter returns zero rows instead of another tenant's books. The failure mode
changes from *silent data leak* to *obviously empty result*.

### 2.3 Secondary wins

- **Cached balances stop drifting.** `updateAccountBalances()` is currently fire-and-forget
  (`.catch(console.error)`), so a failure silently desynchronises `Account.currentBalance`
  from the ledger. In Postgres the balance becomes a view over the ledger — derived, never
  stored, never stale.
- **Entry numbering stops racing.** Reversal numbers are currently generated by
  string-sorting `JE-REV-%` and incrementing, relying on a unique index to catch
  collisions. A Postgres sequence removes the race.
- **Referential integrity.** A journal line can currently reference a deleted account.
  Foreign keys make that impossible.
- **The Mongoose hot-reload problem disappears.** No more restarting `next dev` after
  every schema edit.

### 2.4 Timing

There is one pilot tenant with real data. This is the cheapest this migration will ever
be. Once multiple tenants hold live financial history, cutover windows stop being
negotiable and the effort roughly doubles.

|---|---|

**The 270 aggregation pipelines are the bulk of the work.** No tool converts them; each
is a hand rewrite into SQL. Estimate **3–6 months** for one developer. Any estimate in
weeks is wrong.

Mitigating factor: the data layer is well contained. `app/mongodb/` holds most of it,
which is why a swap is feasible at all.

## 4. Target architecture

### 4.1 Layering

Current leakage — 131 files outside `app/mongodb/actions/` import Mongoose models
directly (53 in `app/mongodb/queries/`, 7 in `app/mongodb/services/`, the rest scattered
through `app/dashboard/` pages and `app/api/` routes).

Target:

```
app/dashboard/**  app/api/**        <- UI + transport. No DB imports.
        |
        v
app/db/actions/**                   <- 'use server' entry points, auth + validation
        |
        v
app/db/repositories/**              <- all SQL. Drizzle queries live here, only here.
        |
        v
app/db/schema/**                    <- Drizzle table definitions
```

The rule we did not have before: **nothing above `repositories/` writes SQL, and nothing
below it reads the session.** Tenant scoping is applied at the repository boundary *and*
enforced by RLS underneath, so a mistake in one layer is caught by the other.

`app/mongodb/` is retained untouched during the slice so both stacks run side by side.

### 4.2 Why Drizzle over Prisma

With 270 pipelines to port, a large share of this codebase is reporting SQL — aging
reports, trial balance, P&L, COGS rollups. Prisma's query builder handles CRUD well but
forces `$queryRaw` for analytics, at which point type safety is lost. Drizzle stays close
to SQL, keeps types through raw fragments, and has no query-engine binary — which matters
for serverless cold starts on Vercel.

Trade-off accepted: Prisma has the better migration tooling and a larger ecosystem. We
use `drizzle-kit` for migrations and accept a slightly rougher DX in exchange for
type-safe reporting queries.

### 4.3 The two invariants, enforced in the database

**Money.** All monetary columns are `NUMERIC(19,4)`. No exceptions, no floats.

**Balance.** A journal entry cannot exist unbalanced. Enforced by a deferred constraint
trigger that fires at COMMIT — allowing lines to be inserted one at a time inside a
transaction, but refusing to commit if they do not sum to zero:

```sql
CREATE CONSTRAINT TRIGGER je_must_balance
  AFTER INSERT OR UPDATE OR DELETE ON journal_lines
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION assert_journal_balanced();
```

Exact equality — `SUM(debit) = SUM(credit)` — with no tolerance window, because NUMERIC
makes the tolerance unnecessary.

**Tenancy.** Every tenant-scoped table carries `company_id` and has RLS enabled:

```sql
ALTER TABLE journal_entries ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON journal_entries
  USING (company_id = current_setting('app.company_id')::uuid);
```

The application sets `app.company_id` once per request, in the repository layer's
connection acquisition. Forgetting a `WHERE company_id` clause then yields zero rows
rather than a cross-tenant leak.

### 4.4 Balances become derived, not stored

`Account.currentBalance` is deleted as a column. It becomes a view:

```sql
CREATE VIEW account_balances AS
SELECT a.id, a.company_id,
       CASE WHEN a.normal_balance_side = 'debit'
            THEN SUM(l.debit) - SUM(l.credit)
            ELSE SUM(l.credit) - SUM(l.debit)
       END AS balance
FROM accounts a
LEFT JOIN journal_lines l ON l.account_id = a.id
LEFT JOIN journal_entries e ON e.id = l.entry_id AND e.status = 'posted'
GROUP BY a.id;
```

If this proves too slow at volume, it becomes a `MATERIALIZED VIEW` refreshed on post —
but it never goes back to being a hand-maintained field updated by a fire-and-forget
promise.

## 5. Schema mapping — accounting core

Embedded arrays become child tables. Cached denormalised fields (`accountCode`,
`accountName`, `accountType` on each line) are dropped in favour of joins, except where
they must be frozen for audit.

| Mongo | Postgres | Note |
|---|---|---|
| `_id` (ObjectId) | `id UUID DEFAULT gen_random_uuid()` | See §6.1 for id mapping during backfill |
| `JournalEntry.lines[]` | `journal_lines` table, FK to `journal_entries` | Cascade delete |
| `JournalEntry.party.{type,id,name}` | `party_type`, `party_id` FK, no cached name | Name comes from join |
| `lines[].accountCode` / `accountName` | `account_code_at_posting` / `account_name_at_posting` | **Immutable snapshot**, not a cache — a posted entry is an audit record (§8.7) |
| `JournalEntry.relatedDocuments.*` | `source_type` + `source_id` polymorphic pair | Replaces 12 nullable id fields |
| `Account.ancestors[]` + `path` | `parent_id` + `ltree` path | Native hierarchy queries |
| `debit` / `credit` `Number` | `NUMERIC(19,4) NOT NULL DEFAULT 0 CHECK (>= 0)` | |
| `entryNumber` string-scan | `SEQUENCE` per company | Race removed |
| `status` enum | Postgres `ENUM` type | |

Line-level `CHECK ((debit > 0) <> (credit > 0))` replaces the `validateLines()` method —
a line must have exactly one of debit or credit, non-zero.

## 6. Migration strategy

### 6.1 Vertical slice first

Slice: **the accounting core** — `accounts`, `journal_entries`, `journal_lines`,
`fiscal_periods`, `companies`. Chosen because it is the highest-value module, it exercises
every hard pattern (hierarchy, embedded arrays, transactions, aggregation reporting, RLS),
and everything else in the ERP posts to it.

Deliverables for the slice:
1. Drizzle schema + migrations for the five tables
2. RLS policies and the balance trigger
3. Repository layer replacing `journal-actions.js` and `account-actions.js`
4. The three reports ported to SQL: trial balance, AR aging, AP aging
5. Backfill script for the pilot tenant, with reconciliation
6. Measured effort, to price the remaining 64 models honestly

We do not proceed past the slice until it is proven and the numbers are in.

### 6.2 ObjectId → UUID

Mongo ObjectIds are 12 bytes, UUIDs are 16. They are not convertible. The backfill
maintains an `_migration_id_map` table (`old_object_id TEXT PRIMARY KEY`, `new_uuid UUID`)
populated in a first pass, then used to resolve all foreign keys in a second pass. The map
is retained after cutover for audit trail and for tracing any support issue back to
pre-migration records.

### 6.3 Cutover for the pilot tenant

With one friendly tenant, we do not need dual-write. Sequence:

1. Announce a maintenance window
2. Freeze writes (`readOnly` flag already exists in the plan-gating code)
3. Run backfill
4. **Reconcile:** trial balance from Mongo must equal trial balance from Postgres, exactly,
   to the cent. Any variance blocks cutover — a variance here is the float drift from §2.1
   surfacing, and each one needs an explicit accounting decision, not a rounding fudge.
5. Flip the connection, unfreeze
6. Keep the Mongo database read-only for 30 days as rollback

Expect step 4 to find discrepancies. That is the point.

| Risk | Mitigation |
|---|---|
| 270 pipelines is an underestimate | The slice measures the real per-pipeline cost before we commit to the rest |
| Reconciliation finds pre-existing float drift | Surface it, decide per-variance with the tenant. Do not paper over |
| Long branch divergence from `jeff-business-suite` | Rebase weekly. Freeze large refactors on the parent branch during the slice |
| Regression in working accounting logic | Domain logic is ported as-is, not redesigned. Reconciliation is the test |
| Serverless connection exhaustion | PgBouncer / Neon pooling from day one, not retrofitted |

## 8. Design corrections made during the port

These are not refactors for their own sake. Each is a defect class the current
schema permits and Postgres can forbid, and each costs almost nothing while a table is
being defined for the first time — and a great deal afterwards.

The rule applied throughout: **an invariant the application currently remembers
to check becomes something the database will not allow to be violated.**

### 8.1 Fulfilment source is decided by the absence of a field

`Invoice.complete()` selects which inventory account COGS credits like this:

```js
const isFromTechnicianStock = !!(item.relatedRequest?.requestId || item.relatedCheckout?.checkoutId);
const isWBFulfilled = !!item.weighbridgeTicketId;
```

- stock request or checkout → credit **Technician Stock**
- weighbridge → **skip COGS** (already posted at the gate)
- otherwise → credit **Inventory**

So a nullable nested field decides which GL account is credited. "Not from
technician stock" and "the `relatedRequest` field did not persist" are the same
state. That is precisely the `parentAccount` defect (§2 of this document, fixed
separately) — except the consequence there was a flat dropdown, and here it is
stock credited to the wrong account in posted books.

Nothing prevents `relatedRequest` and `weighbridgeTicketId` both being set. The
`if / else if` silently prefers technician stock: precedence encoded as
statement order.

**Correction.** Fulfilment source becomes explicit, mandatory and enumerated,
with the reference required to match:

```sql
fulfilment_source     fulfilment_source_enum NOT NULL,  -- inventory | stock_request
                                                        -- | checkout | weighbridge
stock_request_id      uuid REFERENCES stock_requests(id),
checkout_id           uuid REFERENCES item_checkouts(id),
weighbridge_ticket_id uuid REFERENCES weighbridge_tickets(id),

CHECK (
     (fulfilment_source = 'inventory'     AND stock_request_id IS NULL
                                          AND checkout_id IS NULL
                                          AND weighbridge_ticket_id IS NULL)
  OR (fulfilment_source = 'stock_request' AND stock_request_id IS NOT NULL)
  OR (fulfilment_source = 'checkout'      AND checkout_id IS NOT NULL)
  OR (fulfilment_source = 'weighbridge'   AND weighbridge_ticket_id IS NOT NULL)
)
```

A line cannot be ambiguous, so the precedence question stops existing. A missing
reference is a hard error at insert rather than a silent switch to a different
account.

### 8.2 Two sources of truth for provenance

Provenance is recorded twice: `invoice.source.{type, requestId, checkoutIds[]}`
at the header, and `item.relatedRequest` / `item.relatedCheckout` per line.
Nothing keeps them consistent, so an invoice can read `source.type = "direct"`
while its lines post against Technician Stock. Any report grouping by
`source.type` then disagrees with the ledger.

Note also the shape mismatch: `source.checkoutIds` is an array, while
`item.relatedCheckout.checkoutId` is singular.

**Correction.** The header value is derived from the lines, not stored. Header
provenance becomes a query, so the two cannot diverge.

### 8.3 COGS double-posting is prevented by a read-then-check

For a weighbridge sale, cost is recognised at gate crossing on the **weighed**
quantity, and the invoice posts revenue only. That is deliberate and correct:
for bulk commodities the weighed quantity is the truth, and the stock physically
left at that moment.

Both orderings are handled today, by a mutual-exclusion protocol:

- **WB first:** connector posts `goods_dispatch`, stamps
  `item.weighbridgeTicketId`; the invoice later sees the flag and skips COGS.
- **Invoice first:** connector reads `linkedInvoice.status === "completed"`, sets
  `invoiceAlreadyPosted`, and skips both the stock movement and the journal
  entry.

Two weaknesses:

**It is a TOCTOU race.** The connector reads invoice status, then creates its
journal entry, with no transaction spanning both and the invoice posting in a
different process. An invoice posted inside that window produces COGS twice.

**The costed quantity depends on operational timing.** If an invoice bills
1,800 kg and the bridge weighs 1,750:

| Order | COGS posted on |
|---|---|
| WB first | 1,750 — what left |
| Invoice first | 1,800 — what was billed |

Same shipment, different cost of sales, decided by which system ran first. In
the invoice-first branch the discrepancy surfaces only as warning text asking an
accountant to "verify the invoice quantity matches the WB net weight" — a manual
step with nothing recording whether it happened.

**Correction.** Make "COGS has been posted for this line" a uniqueness
constraint rather than a flag two systems agree to check:

```sql
CREATE TABLE cogs_postings (
  invoice_line_id   uuid PRIMARY KEY REFERENCES invoice_lines(id),
  posted_by         cogs_source_enum NOT NULL,   -- 'invoice' | 'weighbridge'
  journal_entry_id  uuid NOT NULL REFERENCES journal_entries(id),
  quantity          numeric(19,4) NOT NULL,
  posted_at         timestamptz NOT NULL DEFAULT now()
);
```

The primary key does the work: whoever posts first inserts, the second attempt
takes a unique violation. No read-then-check, therefore no race. It also records
which quantity was costed and by whom, so the 1,750-vs-1,800 discrepancy becomes
queryable data instead of a warning string.

### 8.4 Stored derived values

The same pattern already corrected for `Account.currentBalance` (§4.4) and
`Party.cachedBalance` (§5) recurs:

| Field | Defined as | Problem |
|---|---|---|
| `Product.inventory.quantityAvailable` | `quantityOnHand - quantityCommitted - quantityOnHold` | stored, so it can disagree with its own inputs |
| `Payment.totalAllocated` | sum of `allocations[].amountAllocated` | recomputed in a pre-save hook; a write that bypasses the hook leaves it stale |
| `Payment.unappliedAmount` | `Math.max(0, amount - totalAllocated)` | as above, and the `Math.max(0, …)` clamps over-allocation to zero rather than showing it |

**Correction.** Generated columns or views. A value that is a function of other
columns is never stored.

### 8.5 Float tolerances

`0.01` guards appear throughout as compensation for float64 arithmetic —
`isFullyApplied()` in `payment.js`, the over-allocation guard
(`totalAllocated > amount + 0.01`, which permits over-allocating by up to a
cent), the balance check in `JournalEntry`, and the zero-balance filters in the
report service.

**Correction.** `numeric(19,4)` throughout and exact comparison. The tolerance
exists to hide float residue; exact decimals do not produce residue. Where a
tolerance is genuine accounting policy rather than a workaround, it must be
stated as policy and applied deliberately — not inherited from a workaround.

### 8.6 Denormalised copies

`requestNumber`, `technicianId`, `technicianName`, `checkoutNumber` and
`weighbridgeTicketNumber` are cached onto invoice lines; `accountCode` /
`accountName` were cached onto journal lines (already dropped in the accounting
core).

**Correction.** Foreign key plus join. Cache only where a value must be frozen
for audit — e.g. the price actually charged — and say so explicitly at the
column.
